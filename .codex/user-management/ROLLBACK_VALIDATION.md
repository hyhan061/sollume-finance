## 구현 결과

- `deploy-oracle.sh`: 새 이미지 pull 전에 실제 실행 이미지·설정·DB를 캡처하며, 실패하면 서비스 교체를 중단합니다. 배포 실패 시 복구 지점만 안내하고 자동 롤백하지 않습니다.
- `scripts/release_snapshot.py`: 이미지 ID 고정·오프라인 이미지 보관·SQLite 일관 백업·비공개 키 보관·체크섬/HMAC 검사·호환성 점검·503 차단 후 복구를 구현했습니다.
- `rollback-oracle.sh`: 가상환경 Python을 선택하고 기본 실행은 변경 없는 사전 점검입니다. 실제 복구에는 `--apply`가 필요합니다.
- 일반 보안 버전 복구는 최신 비밀번호·MFA·계정 상태·화면별 권한과 업무자료를 유지하고 기존 세션·등록 코드·다운로드 권한만 폐기합니다.
- 인증 도입 전 복구는 최신 사용자 DB를 먼저 보관한 뒤 명시적으로 과거 사용자 DB를 복원합니다. 최근 정지·삭제·이름 변경·비밀번호 변경에 따른 옛 접근권한 부활을 막고, 공개 접속은 계속 503으로 유지합니다. 필요한 기존 계정의 새 비밀번호는 별도 운영자 명령에서 숨김 입력합니다.
- 기존 CPU·메모리·읽기 전용 마운트·루프백 포트·파일 소유권을 유지합니다. UID/GID 보존은 실제 소유권 변경 없이 모의 root 검사로 검증했습니다.

신규 13개는 단위 8개와 통합 결과를 확인하는 5개로 구성됩니다. 통합 5개는 **같은 실제 리허설 1회**의 결과를 공유하며, 55개 검사를 서로 다른 55번의 독립 배포로 집계하지 않습니다. 기존 회귀 테스트 이후 해당 인증·업무 소스가 바뀌지 않았음을 해시로 다시 확인했습니다.

실제 Docker/Compose와 Nginx·SQLite·HTTPS·MFA를 사용하여 다음을 확인했습니다.

- 캡처 시 WAL에 커밋된 자료 포함, 조회 전용 점검 시 미반영 WAL 거부, 기본 명령의 무변경, 변조·손상·잘못된 경로/환경변수/마운트 거부.
- 태그가 이동해도 저장한 이미지 ID로 복구, 최신 사용자 정보·MFA 암호문·권한·거래처·발주 파일 유지, 기존 로그인 쿠키 거부, 보존한 MFA로 HTTPS 로그인 성공.
- CPU·메모리·마운트·읽기 전용 루트·tmpfs·루프백 포트 보존, 셸 export 값에 의한 현재 .env 키 덮어쓰기 방지, 인증 서비스가 누락된 장애 상태에서도 안전한 복구.
- Nginx·이미지 로드·서비스 시작·상태 검사·중단의 **5개 실패 지점은 명시적으로 주입**했습니다. 각 경우 실제 HTTPS 503과 최신 DB 백업을 확인하고 같은 복구 지점으로 재시도에 성공했습니다.
- 실제 구버전 이미지로 복구해 공개 503과 계정 제한 유지, 폐기한 옛 비밀번호 거부, 미변경 bcrypt 계정 로그인 성공, 비TTY 변경 거부, 실제 PTY의 숨김 입력과 새 비밀번호 로그인 성공.

## 범위와 한계

시험은 원본 DB·키를 마운트하지 않은 합성 자료, 별도 Compose 프로젝트, 임시 루프백 포트에서 수행했습니다. Nginx 호스트 명령은 시험용 컨테이너에 연결하고 upstream은 Docker Desktop의 `host.docker.internal`로 연결했습니다. 임시 자체 서명 TLS를 별도 CA로 검증했으며, 시험 프로세스에서만 게시 포트를 격리 고포트로 대체했습니다. 실제 운영 CLI가 이 고포트를 거부하는 검사도 통과했습니다.

로컬 실행 이미지는 모두 Linux ARM64입니다. 실제 운영 호스트의 systemd, 다른 아키텍처, 외부 방화벽, 운영 인증서, 전역 Nginx 설정과 다른 사이트는 검증하지 않았습니다. 이 결과를 운영 배포 완료로 간주하지 않습니다.
