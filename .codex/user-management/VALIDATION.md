# 구현 및 검증 결과

최신 main(c5b8c88)에서 만든 `codex/strict-user-management` 브랜치에 구현했습니다. 운영 서버·실제 계정·환경 키는 변경하지 않았습니다.

관리자 화면에서 직원 생성, 활성 상태, 관리자 역할, 화면별 허용 권한, 비밀번호·인증 앱 초기화, 잠금 해제와 감사 이력을 관리합니다. 모든 직원은 비밀번호와 인증 앱의 TOTP 등록·검증을 완료해야 업무에 접근합니다. 중요한 관리 변경은 최근 인증을 요구하고 마지막 활성 관리자를 보호합니다.

화면과 업무 작업은 서버에서 권한을 검사합니다. 권한 변경·정지·인증 초기화 시 기존 세션을 폐기합니다. 다운로드는 생성한 직원과 정확한 로그인 세션에 귀속하며 15분 만료·화면 권한을 검사합니다. 기존 media 경로는 차단합니다. 출력 파일도 세션·생성 건마다 분리하여 같은 파일명의 덮어쓰기를 방지합니다.

| 검증 | 결과 |
|---|---|
| 보안 핵심·HTTP·실제 Streamlit UI·배포 설정 | 75개 통과 |
| 기존 정산서·기간 요약 회귀 | 163개 통과 |
| 실제 Nginx·TLS·WebSocket·업로드·다운로드·인증 서버 장애 | 84항목 통과 |
| 실제 Chrome: MFA 등록, 관리자 폼 권한 변경, 재로그인, 정지, 로그아웃 | 6개 시나리오 통과 |
| 실제 Docker 이미지 빌드 | 성공 |
| 기존 사용자·거래처 DB와 발주 데이터 | 기준 파일 9개 SHA256 변경 없음 |

검증은 합성 임시 인증 계정·DB로 수행했습니다. 실제 업무 데이터는 검증 시작 전 해시와 대조했고, 스키마 전환의 계정 ID·해시·로그인 이력 보존은 기존 구조를 재현한 임시 DB로 확인했습니다. TLS 검증의 소스 해시 일치와 임시 컨테이너·네트워크 정리도 확인했습니다.

## 운영 적용

[운영 안내](OPERATIONS.md)를 따라 기존 DB와 인증 키를 백업하고 HTTPS·환경 설정을 적용해야 합니다. 기존 계정은 첫 접속 때 운영자가 발급한 일회용 등록 코드로 인증 앱을 등록하고 비밀번호를 변경합니다. 기존 일반 직원의 초기 업무 권한은 보존하므로 공개 전에 관리자 화면에서 직원별 허용 화면을 검토해야 합니다.

로컬 Chrome 검증은 loopback 개발 모드, Nginx 검증은 격리된 HTTPS 시험 스택입니다. 실제 운영 서버 배포·외부 방화벽 적용·Windows 실행은 이번 작업에서 수행하지 않았습니다. 이미 표시되거나 내려받은 자료를 소급 회수하는 기능은 없습니다.

상세 증거는 `implementation-results.json`, `regression-auth-and-accounting-20261014.json`, `runtime-results.json`, `browser-results.json`에 보관했습니다. 브라우저 검증을 재실행할 때는 가상환경의 시험 도구 `playwright`와 로컬 Chrome이 필요하며 이는 운영 requirements에 포함하지 않았습니다.
